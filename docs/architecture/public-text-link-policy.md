# Proposed public-text link policy

Status: design for review; relates to #7388. This document does not activate a list, change a schema or API contract, rewrite existing content, or authorize deployment. The source inventory describes the repository at `d1a588810`; it is not a production-content audit.

## Policy and approval boundary

The agreed policy is to replace disallowed links with `[link removed]` in all public user text, for adults and minors alike. Existing email, telephone, contact-site and contact-scheme removal stays in place with `[contact removed]`. A host must be explicitly approved; subdomains need a separate explicit permission. Educational suffixes receive no blanket exemption. Moderators maintain a versioned, audited list. A host's approval is not a guarantee about every page, user contribution or redirect on that host.

Implementation, the initial exact host entries, staff grants, activation and treatment of historical content still require review. The detailed algorithms, limits and workflow below are proposals. Do not import a client application's trusted-domain list as approval, execute the existing historical sanitizer, or change external project source as part of preparing this design.

## Shared decision and span model

Use one server policy engine for preview, writes and public reads. Conceptually it returns sanitized text, replacement spans with reason codes, and the immutable policy revision used. This is an internal design, not a new response schema. No endpoint/header/payload is added here; any future public preview or metadata contract needs an OpenAPI-first change and semantic review of generated output.

1. Validate UTF-8 and existing field limits. Keep null distinct from empty. Work on a bounded candidate stream with original UTF-8 byte spans; maintain an offset map for normalization, entity decoding and removed invisibles.
2. Detect and reserve existing contact spans first. Contact removal wins over the host list, including contacts on an otherwise approved site. Keep `[contact removed]` and existing profanity behavior; do not run profanity's leet/homoglyph folding over hostnames.
3. Recognize URL-like candidates in remaining text, including absolute/scheme-relative links, `www.`, bare Unicode/ASCII domains, spaced dot obfuscation and markup destinations. Scan all candidates, not only the first or a suffix from today's username regex. Detection must not itself make a candidate allowed.
4. Normalize/validate each candidate, decide against one policy revision, merge overlapping spans and replace disallowed spans from the end of the original string with `[link removed]`. Preserve surrounding punctuation and unrelated prose. A contact-overlapping construct must not leave a clickable residual destination.
5. Escape output for its final HTML/attribute/JSON context. Sanitization is not HTML escaping or an HTML safety sanitizer. Any future linkifier must use the validated canonical destination rather than independently reparsing the preserved original spelling. Reprocessing placeholders must be idempotent and must not turn a removed link into markup.

Proposed bounds: retain the existing field limits, at most 256 candidates per field, 4,096 bytes per candidate and bounded markup nesting. Over-limit or malformed-UTF-8 submissions receive a normal field validation failure, without silently accepting an unscanned tail, truncating content or partially saving other fields. The implementation must set measured CPU/memory budgets and test worst cases without catastrophic regular expressions. On an invalid policy revision, retain the last verified revision; if none exists, decline public-text writes rather than pass raw text. Public rendering must use a safe unavailable-text fallback, not leak raw input. These availability/error details require compatibility review before activation.

## Host normalization and decision rules

Proposed default transport is HTTPS; a future HTTP exception requires explicit per-entry approval and must not silently upgrade or fetch a URL. Bare/`www.`/scheme-relative candidates are interpreted as HTTPS for matching only. Relative markup destinations are disallowed user links; server-generated internal navigation remains outside user text.

Use a browser-compatible URL parser with explicit pre-validation, rather than treating `parse_url()` as validation. PHP documents both parser inconsistencies and strict [WHATWG/RFC URI alternatives](https://www.php.net/manual/en/function.parse-url.php). Proposed implementation uses PHP 8.5’s `Uri\WhatWg\Url` API, subject to verifying its availability in every supported runtime, with a shared conformance corpus against browser URL interpretation. If unavailable, select a maintained browser-compatible parser explicitly; do not fall back silently to permissive component splitting. Reject backslashes, controls, malformed authority, credentials/userinfo, encoded host separators and ambiguous authority before parsing; do not let browser recovery reinterpret an approved-looking prefix.

Normalize hosts with UTS #46 non-transitional IDNA, STD3, Bidi and ContextJ checks, lowercase ASCII output and explicit error checking. PHP's [IDNA conversion API](https://www.php.net/manual/en/function.idn-to-ascii.php) exposes UTS #46 errors; a failed or ambiguous conversion is disallowed. A Unicode display form is not an additional allowlist key. No confusable/transliteration mapping may convert an unrelated host into an approved host. Normalize recognized Unicode dot variants, remove the reviewed invisible/control set for detection with offsets retained, and reject dangerous controls in the actual authority. Strip at most one DNS terminal dot for comparison; repeated/empty labels remain invalid. Validate DNS label/host lengths and the normalized host returned by the URL parser against the IDNA result. Test ICU/parser version changes before rollout.

A candidate is allowed only if its normalized host equals an enabled entry, or the entry explicitly allows subdomains and the host ends with `.` plus that entry. This never permits sibling/suffix lookalikes. Reject userinfo even when its actual host is approved. Reject literal IPs, alternate numeric IP forms, localhost/single-label targets, non-default ports and schemes outside the approved entry. Contact schemes retain contact removal; other schemes such as executable/data/file/custom app URLs receive link removal. Do not decode percent-encoded authority into an approval. Ordinary percent encoding in a valid path/query is not a new hostname.

Bare-domain detection needs a versioned, locally bundled public-suffix corpus plus explicit approved-host detection, not an online lookup or `.edu` permission. Scheme/`www.` candidates are detected regardless of suffix. Unknown but syntactically domain-like suffixes must be classified conservatively as link candidates rather than silently passing; preview explains likely false positives such as dotted filenames. Do not exempt file extensions wholesale: a filename-looking suffix can also be a real domain. Avoid treating decimals, ordinary sentence stops or account handles as domains without a valid domain shape. A PSL update affects tokenization and needs the same corpus review/versioning as parser changes.

## Markup, punctuation and redirects

Current plain-text fields remain plain text; do not enable HTML or Markdown rendering. Recognize potential Markdown inline/reference/autolink/image destinations and HTML `href`/`src` destinations in a bounded tokenizer, including entity-encoded attributes. For a disallowed destination replace the complete link/image construct, including any misleading approved-looking label. For an allowed construct, separately sanitize its visible label and any domain text in a title; retain the existing plain-text presentation. Scan fenced/inline code text as public prose for displayed links without modifying uploaded program code. If a later field deliberately supports rich text, use its actual AST and remove disallowed anchors/media safely rather than regex-editing serialized HTML.

Trim sentence punctuation only when it is outside a balanced URL component: retain balanced parentheses in paths, exclude unmatched closing brackets/quotes and final prose commas/stops. Map HTML entities exactly once in markup context, preserve source offsets, and do not repeatedly percent-decode or HTML-decode arbitrary prose. Examples and browser tests must cover nested labels, reference links, multiline attributes and encoded control separators.

Shorteners and general redirect services are not eligible seed entries. Do not fetch, resolve DNS, follow redirects, inspect remote pages or call a URL-expansion service during preview/write/read. Reviewers must record known redirect endpoints on proposed allowed hosts; deny those endpoints in a small reviewed non-regex rule catalog or decline that host if the restriction cannot be enforced reliably. A disallowed URL nested visibly in a path/query/label is not made safe by wrapping it in an allowed host; the candidate tokenizer must remove the enclosing redirect-like construct when that destination is recognized. Never claim this can infer every encoded or future server redirect: an approved host can change behavior or contain harmful content. Reports and rapid revocation remain necessary; approvals of broad user-content/shared hosting require particular scrutiny.

## List governance and seed approval

Proposed entries record canonical ASCII host, Unicode display form, explicit subdomain permission (default false), approved schemes (default HTTPS), purpose, ownership/review evidence, reviewer, review/expiry date and status. No wildcard host, public suffix, regular expression, IP literal or URL path masquerades as a host entry. Known redirect restrictions are reviewed alongside entries. The active revision is immutable, monotonically versioned and content-hashed; audit records before/after diff, actor, approver, reason and activation time. Revocation creates another revision; restoring a prior content set still produces a new revision.

Current `config/packages/security.php` gives `ROLE_MODERATOR` the user role; admin inherits moderator and super-admin inherits admin. Several specialist roles also inherit admin. Sonata admin access alone therefore cannot safely express narrowly delegated list maintenance. Propose a dedicated server-side management/activation capability with explicit staff grants, checking existing moderator/admin hierarchy plus that capability, CSRF protection and audit on every action. A studio owner or content approval flag grants no policy privilege. Maintainers approve initial grants and seed activation; assigned moderators maintain subsequent entries with a second staff approval for additions/subdomain expansion. Emergency revocations may be immediate with mandatory audit and subsequent review. Exact permissions/storage/UI are a later implementation design, not role assignments in this PR.

The initial candidate set is limited to individually verified owned community hosts and reviewed educational sources. Candidate examples for review include `catrobat.org`, `share.catrobat.org`, `scratch.mit.edu` and specific Wikipedia language hosts. This is not an approved seed list. Do not infer permission for every subdomain, `.edu`, country education suffix, GitHub/shared hosting, deprecated services or every host in a client trusted-domain file. The seed review must record exact host ownership, purpose, redirects and whether content is user controlled; domain expiration/ownership changes trigger review. No seed import, DNS/HTTP review automation or policy activation is authorized here.

## Preview, evidence and compatibility

Before submission explain: “Links are allowed only to approved sites. Other links are replaced with [link removed]. Contact details are removed.” Show the exact sanitized result and distinguish contact/link replacements without reproducing unsafe clickable targets in warnings. The save must recompute server-side under a single active revision; if the preview revision changed, return a reviewable field warning/re-preview instead of saving a different result silently. Existing clients without preview still receive sanitized public text through their established response flow. Name uniqueness, required/minimum length and maximum length checks must evaluate the final text too; a collision after replacement is a field error, not an automatic rename or partial save. Preserve existing error conventions until a separately reviewed API contract declares any additional detail.

Store neither raw submitted URLs nor full unsanitized text in ordinary access logs, analytics or exception messages. Moderation evidence, if needed, belongs in the existing restricted report/appeal process with existing retention/deletion rules, not a new indefinite raw-content archive. The current sanitizer does not itself establish a raw-submission evidence vault; implementing a new snapshot store or retention period needs separate approval. A removal record may retain revision/reason, actor/content reference and redaction counts without the raw target. Moderators can inspect existing authorized source/evidence views; public previews and exports must not accidentally disclose restricted evidence. Private account-data exports keep their established purpose and access, with raw-versus-public fields explicitly reviewed.

## Historical content, projections and rollout

No historical rewrite or render-time enforcement is activated by approving this design. The proposed initial implementation sanitizes new/edited public prose at the shared boundary and adds a policy-aware public view covering legacy records, translations/imports and alternate projections. Whether to activate that view for historical content is a distinct maintainer decision after a non-writing impact report and compatibility review. Merely adding write-time filtering leaves existing unsafe destinations visible; document that limitation if historical filtering is deferred. A migration alternative needs explicit authorization, backup/rollback design, scoped dry-run, retention review and handling of archives/translations/indexes; do not run the existing sanitize-existing command as a shortcut.

All derived caches and projections need the effective policy revision and source revision in their keys or an equivalent invalidation mechanism. This includes translations, search snippets/index fields, project/studio lists, remix labels, notification payloads, HTML/JSON response caches and browser/CDN responses. Prefer raw internal search data plus policy-aware public projection initially; an index containing sanitized text needs a coordinated reindex on rule changes and must never become a raw public fallback. Filter translated output after provider/cache lookup; invalidate prior sanitized translations when source or policy changes. Never let title/metadata/excerpt fields leak text omitted from the main body. Existing copied browser content cannot be erased by server invalidation.

Proposed stages: inventory/seed/permissions and corpus approval; offline impact report without writes or remote link fetching; observation-only revision with aggregate reason/count metrics and no raw targets; preview/legacy-client compatibility testing; separately authorized future-write activation; separately authorized historical public-view activation; optional reviewed migration. Keep flags separate for preview, future writes and historical reads, with rollback to a reviewed revision and defined safe rendering fallback. List refresh failure must not switch filtering off. Deployment, cache purges, reindexing and historical jobs require their own release authorization. Confirm behavior when an entry is removed and later re-approved: old stored replacements do not magically recover original text.
