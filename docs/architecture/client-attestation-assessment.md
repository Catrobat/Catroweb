# App-attestation feasibility and abuse-measurement proposal

Status: assessment only, related to #7387. No attestation enforcement, client integration, cloud configuration, new production measurement, schema/API change or deployment is authorized by this document. The discussion stays open. No client/cloud team acceptance is assumed, and no outreach has been performed.

## Finding and recommendation

There is not enough evidence to recommend attestation enforcement. Limited aggregate activity or content-report totals do not identify automation, establish its rate, measure rejected attempts or distinguish legitimate client populations. Reports can be delayed, incomplete or disputed; a reported action is not automatically automated abuse. An interruption or atypical traffic window is not a normal baseline.

First agree a privacy-preserving measurement plan and have the relevant owners assess feasibility. If evidence later justifies a trial, propose optional, observation-only attestation with no change to access or existing limits. Only after separate review should a risk signal contribute to a proportionate challenge or action-specific limit. Missing/unsupported verdicts must not become a blanket denial rule. Browser users, older clients, alternative distributions and unsupported devices need functional paths. Do not embed a shared secret or API key in an app.

A valid app/device signal does not authenticate an account, authorize an action, prove a human is present, validate uploaded content or prevent a real-device farm. Attackers can relay genuine verdicts or use the browser API instead. Existing authentication, access checks, CSRF, rate limits, content controls and moderation remain necessary; a valid verdict must not exempt a request from them.

## Proposed abuse-measurement plan

No collector, dashboard, query job or retention change is implemented here. Approve purpose, dimensions, access and retention before collecting anything new. Prefer bounded aggregate counters at the decision point over copying identifiable application logs.

| Question                                  | Proposed aggregate evidence                                                                                                                                                                                                           | Limits / privacy guard                                                                                                                                                                                                    |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Where is abuse costing effort?            | Attempts, accepted actions, validation failures and rate/captcha rejections by action family: registration, login, upload, comments, reactions/follows and reports. Compare completed actions to later confirmed moderation outcomes. | Do not aggregate every 4xx as abuse or reveal content/passwords/tokens. Count attempts and outcomes with explicit denominators; avoid double counting automatic retries.                                                  |
| Which legitimate users would be affected? | Coarse web/native/unknown cohorts, broad app-version ranges and platform/support categories, action completion, challenge abandonment and recovery.                                                                                   | User-Agent/distribution claims remain unverified. Preserve unknowns; no exact UA, IP, account ID or per-device label in metric dimensions. Suppress small cells and avoid combining dimensions into identifiable cohorts. |
| Are controls working?                     | Limiter accepted/rejected, captcha disabled/missing/verified/failed/provider-error, response classes and latency buckets; compare a normal baseline with proposed observation windows.                                                | Disabled/test behavior must not inflate success. Exclude outages, tests and interrupted traffic windows; annotate instrumentation changes. Shared networks and legitimate bursts can explain rejections.                  |
| Would a verdict add information?          | If a separate trial is approved: absent/not-requested/unsupported/error/quota-exhausted/verified/invalid-binding cohorts, verification latency and cost, completion and independently confirmed abuse outcomes.                       | Missing or unsupported is not “failed integrity.” Do not log verdict tokens, challenges, certificate chains, precise device properties or payload hashes as analytics identifiers.                                        |
| Is there harmful friction?                | Aggregate client completion/recovery, support/appeal outcomes and a bounded authorized human review of disputed/confirmed cases.                                                                                                      | False-positive estimates require adjudicated legitimate samples; not every report or challenge failure supplies a label. Do not claim correlation proves automation or causality.                                         |

Propose an owner-approved normal-traffic baseline and observation window spanning ordinary usage patterns, with minimum sample requirements set before interpreting results. Sparse cohorts mean “insufficient evidence,” not zero abuse. Compare like-for-like actions and populations, documenting seasonality and releases. A non-random opt-in group can differ systematically from unsupported clients; a claimed reduction needs an appropriate study design, not a before/after chart alone.

Use low-cardinality counters and latency histograms, with aggregate daily/weekly reporting and an approved short retention period. Set the exact retention and small-cell threshold before collection; no indefinite raw-event store is implied. If linking an action to a later moderation decision requires a temporary join, review its legal purpose and implement it inside the existing restricted data boundary; export only aggregates and delete the join material on schedule. Hashing an account/device/IP does not make it anonymous. Do not introduce device fingerprinting, cross-app tracking, device-recall flags or stable hardware IDs for this assessment. Audit dashboard/export access, apply deletion requirements, and keep existing private evidence private.

## If justified later: bounded trial design

Start with no enforcement and no privilege increase for a good verdict. Sampling, endpoint scope and quota budgets must be explicit. Preserve existing authenticated/anonymous behavior and limits for browsers, older apps, alternative builds, unsupported devices and absent tokens. Do not add a shared client secret, infer trust from `X-Auth-Mode`/User-Agent or require everyone to install/update an official store client. Quota exhaustion/provider outage/timeout are distinct unavailable outcomes, not grounds to suspend an account or destroy a session.

For a later protocol, bind proof to the action, method/route, canonical payload digest, intended account/session where appropriate, expiry and a single-use server challenge or equivalent reviewed replay mechanism. Do not send plaintext passwords, tokens or content to a provider. Review hashed-data privacy too. Validate app/signing identity, configured environment/audience, timestamp/binding and the platform's cryptographic result on the server; never accept a client “verified” boolean. Keep retry/idempotency semantics explicit, bound verification work and token sizes, and avoid proof reuse as a long-lived bearer credential. Provider replay features do not replace application checks or authorization.

Only if independently reviewed observation shows benefit should maintainers consider a separately approved, action-specific step-up: for example, an accessible challenge or a temporary risk-sensitive limit. It must have a working browser/old-client/alternative-build path, clear errors, recovery and appeal, and a stop criterion for legitimate-user harm. Do not silently lower limits for everyone who lacks proof. Exact thresholds/actions remain undecided, and client teams have not agreed to implement them.

| Observation tests       | Verified/invalid/absent/unsupported/timeout/quota/provider errors; zero trust relaxation; bounded processing; no raw proof/PII logging; metrics unknown/small-cell rules.                                               |
| Legitimate-client tests | Web, legacy app, alternative signing/store, school/no-GMS, offline/slow network, reinstall/key loss, accessibility, concurrent/retried uploads and cancellation. These are required cases, not verified runtime claims. |
| Optional step-up review | Measured benefit plus adjudicated false-positive/friction evidence, accessible fallback, recovery/appeal, thresholds and owner acceptance. A genuine verdict alone is never a universal allow rule.                     |
| Release approval        | Feature flags/kill switch, quota/outage behavior, privacy deletion and rollback tested; explicit deployment approval. None is authorized by this assessment.                                                            |

The present recommendation stops at measurement and owner feasibility review. The feature discussion remains open; an implementation or enforcement proposal would be a separate decision.
